# Multiband performance measurement

**Date:** 2026-11-04 (updated 2026-11-09)

**Status:** measured; per-band architecture retained, with bounded parallel
batches
**Script:** [`scripts/benchmark_multiband.py`](../scripts/benchmark_multiband.py)

This note records the multiband performance decision and its 2026-11-08
parallel amendment. It measures the existing per-band `AnalyzeBands` path
against the real `nec2c` adapter; it is not a synthetic unit benchmark.

## Environment and method

- Linux 7.0.0, AMD Ryzen 7 5825U, 16 threads.
- `nec2c 1.3.3`.
- 15 impedance/SWR points per band.
- 5 pattern frequencies per band at a 5° pattern step.
- Six representative cases: OCFD, G5RV at 3/5/8 bands, and a fan dipole at
  3/8 bands.
- Each produced band run is recorded in a project; the compressed project size
  is measured with `JsonProjectRepository.serialized_size()`.
- Peak RSS is the process maximum reported by `resource.getrusage()` and is
  cumulative across the cases in one process. It is an upper-bound indicator,
  not an isolated per-case measurement.

Reproduce with:

```bash
uv run python scripts/benchmark_multiband.py \
  --nec2c spikes/phase0/build/nec2c
```

## Results

| Design | Bands | Sweep points/band | Pattern freqs/band | Seconds | Compressed MB | Peak RSS MiB | Status |
|---|---:|---:|---:|---:|---:|---:|---|
| OCFD 40 m | 3 | 15 | 5 | 0.46 | 1.96 | 64 | ok |
| G5RV | 3 | 15 | 5 | 0.49 | 2.27 | 168 | ok |
| G5RV | 5 | 15 | 5 | 0.78 | 3.61 | 182 | ok |
| G5RV | 8 | 15 | 5 | 1.27 | 5.94 | 268 | ok |
| Fan dipole 40/20/10 m | 3 | 15 | 5 | 0.45 | 2.75 | 400 | ok |
| Fan dipole wide | 8 | 15 | 5 | 1.35 | 7.35 | 400 | ok |

All six batches completed without solver errors or partial results.

## Decision

Keep the current **one solver run per band** architecture.

The measured batches are small compared with the 32 MB warning and 64 MB
project limit, and the wall time for eight bands is around one second on this
machine. A segmented `FrequencyPlan` and multi-`FR` deck would add a
cross-cutting contract change without a demonstrated need at this point.

Revisit the decision only if one of these becomes true:

- routine runs use 1–2° patterns or much denser sweeps;
- the supported band count or typical point count grows substantially;
- a representative low-end target machine shows user-visible delays; or
- raw solver output becomes a practical project-size problem.

The single-band `SimulationSpec`/`RunSimulation` boundary remains the
regression baseline.

## Parallel band analysis (2026-11-08)

`AnalyzeBands` now accepts `parallel_workers` (1–8; the dialog exposes 1–4) and
runs independent bands in bounded batches. The default command path remains
sequential. This amendment re-runs the same six cases with one and four workers
in separate processes.

Method:

- Same machine, `nec2c 1.3.3`, 15 sweep points and five pattern frequencies per
  band at a 5° pattern step.
- `--workers 1` and `--workers 4` were separate process runs, so the parent
  `ru_maxrss` values are comparable.
- The parent peak RSS is cumulative across all six cases in one process.
- Per-solver memory was measured separately with `/usr/bin/time -v` over the
  16 decks generated by the `g5rv-8` and `fan-8` cases.

| Design | Bands | Sequential s | 4 workers s | Speedup |
|---|---:|---:|---:|---:|
| OCFD 40 m | 3 | 0.46 | 0.33 | 1.4× |
| G5RV | 3 | 0.52 | 0.31 | 1.7× |
| G5RV | 5 | 0.78 | 0.62 | 1.3× |
| G5RV | 8 | 1.36 | 0.87 | 1.6× |
| Fan dipole 40/20/10 m | 3 | 0.54 | 0.30 | 1.8× |
| Fan dipole wide | 8 | 1.39 | 0.94 | 1.5× |

Memory:

- Parent process peak RSS: **402 MiB** sequential, **416 MiB** with four
  workers (+14 MiB, about 3.5%).
- One `nec2c` child peaked at **2.4–2.8 MiB** across the 16 measured band
  decks.
- Four workers therefore add at most roughly **11 MiB** of concurrent solver
  memory for these models, plus the small parent growth.
- Dense wire models allocate more per solver process; the four-worker UI cap
  bounds concurrency, and the dialog can be set to one worker on memory-limited
  systems.

Decision: keep the per-band architecture and allow bounded parallel batches.
The measured speedup is **1.3–1.8×** with four workers, not linear, because
each batch waits for its slowest band and solver startup is a fixed cost. The
sequential `parallel_workers=1` path is unchanged and remains the command
default.

Reproduce with:

```bash
uv run python scripts/benchmark_multiband.py \
  --nec2c spikes/phase0/build/nec2c --workers 1
uv run python scripts/benchmark_multiband.py \
  --nec2c spikes/phase0/build/nec2c --workers 4
```

Use `--case g5rv-8` or `--case fan-8` for the isolated cases used in the
per-solver memory measurement.
