# ADR-0043 — Design frequency versus analysis frequency

- **Status:** Accepted
- **Date:** 2026-11-17
- **Deciders:** Fernando Sclavo, development
- **Related:** UX34–UX37 in [`../AUTONOMOUS_BACKLOG.md`](../AUTONOMOUS_BACKLOG.md),
  [`ADR-0013`](0013-frequency-first-dimension-estimation.md),
  [`../USER_GUIDE.md`](../USER_GUIDE.md)

## Context

The design panel has one frequency field. It is used to seed the template's
starting dimensions, to define the default simulation band, and to choose the
frequency shown in the editor. That is convenient for a frequency-first
workflow, but it mixes two different actions:

1. **Redesigning** the antenna for a new target frequency.
2. **Analyzing** the same geometry at a different frequency.

The UX32/UX33 work made the quad beam, hexbeam, discone, trapped Yagi, and
phased-vertical generators seed their starting dimensions at the requested
frequency and expose **Load starting dimensions**. The remaining question is
whether changing the design frequency should also resize the geometry
automatically.

A universal auto-scale would silently destroy a tuned or solver-refined design.
It would also make an off-frequency SWR or pattern check change the antenna
under test. The opposite extreme, always requiring a manual action, adds
unnecessary friction for a new or untouched design.

There is also a known inconsistency: the Yagi form currently scales its element
lengths and spacings on every frequency change, even after the table has been
edited. That behavior is not extended to other families by this decision and is
recorded as a follow-up item.

## Decision

1. Treat the field as the **design frequency** by default. It describes the
   intended antenna and seeds the starting dimensions.
2. Keep analysis separate. Use **Simulation sweep**, **Band analysis**, and
   measurement comparison to evaluate the same geometry at other frequencies.
   Do not add a separate analysis-frequency field in UX35. If a dedicated field
   is needed later, it requires its own ADR.
3. Never resize an edited or solver-tuned geometry silently.
4. Allow automatic starting-dimension regeneration only when the managed
   geometry is **pristine**, and only for families with a deterministic
   starting-dimension helper.
5. Define **pristine** as: no user edit to any field that the family's starting
   helper overwrites since the last starting-dimension application or template
   seed. Installation and matching fields that the helper preserves do not
   affect the pristine state.
6. The following events mark the managed geometry as non-pristine:
   - a manual edit to a managed field;
   - an optimizer, tuning-assistant, or synthesis result applied to the design;
   - loading a saved project (a saved design always starts non-pristine);
   - undo or redo to a state that was not generated by a starting helper.
7. The following events reset the pristine snapshot:
   - applying **Load starting dimensions**;
   - applying **Estimate Dimensions...**;
   - creating a template or changing template to a generated starting design.
8. When the design frequency changes while the managed geometry is pristine,
   regenerate the starting dimensions as one visible edit. When it is
   non-pristine, do not resize; show a non-modal message and offer the explicit
   action.
9. In a modal generator, the regeneration is local to the dialog and Cancel
   discards it. In an open project editor, it is a normal unsaved form edit:
   applying the design records it in project history. The existing undo/redo
   guard for unsaved form changes applies; undoing an applied design restores
   the applied frequency and geometry.
10. Families without a deterministic starting helper keep their current
    behavior. Do not apply a generic "scale every length" operation. The Yagi
    table's frequency scaling is reconciled under this policy (HF10): it scales
    the element positions and lengths only while the managed table is pristine.
    A table edit, add, remove, or loaded design locks it, and a frequency change
    preserves the geometry and shows the stale warning. The Moxon follows the
    same pristine rule with its explicit 20 m reference action. Do not copy
    either automatic path to families without a deterministic starting helper.
11. The explicit **Scale geometry to frequency** action from UX37 is for
    non-pristine designs. It is never the automatic path.

## Managed fields

The pristine test is per family, not a comparison of every numeric field.

| Family | Managed by the starting helper | Preserved by the helper |
|---|---|---|
| Quad beam | loop side, reflector spacing, director spacing | height, element count, reflector/director scales, transformer, azimuth, radius, material, ground |
| Hexbeam | driver/reflector half-lengths, turning radius, tip gap, feed gap, element separation | height, azimuth, radius, material, ground |
| Discone | cone height, cone radius, disc radius | base height, disc gap, wire count, azimuth, radius, material, ground |
| Trapped Yagi | driven length, reflector/director spacing, trap inset, trap frequency | high-band frequency, trap inductance, element count, scales, height, azimuth, radius, material, ground |
| Phased vertical | element height, spacing, radial length | base height, phase step, amplitude taper, radial count, radial angle, azimuth, radius, material, ground |

A user edit to a preserved field does not lock the dimensions. For example,
changing the quad-beam height does not prevent a later **Load starting
dimensions** from recalculating the loop side and spacing, because the helper
preserves the height.

## UX wording

Use language that distinguishes the two actions:

- Pristine auto-update: **“Starting dimensions updated for 144.000 MHz.”**
- Edited geometry: **“Frequency changed; dimensions were not resized because
  the geometry was edited. Use Load starting dimensions to rebuild them.”**
- Action: **Load starting dimensions**.
- Help: **“The design frequency seeds the starting dimensions. Use Simulation
  sweep or Band analysis to evaluate the same geometry at other frequencies.”**

Do not call the design frequency an analysis frequency. Do not imply that a
simulation result is invalid merely because the analysis frequency differs from
the design frequency.

## Consequences

Positive:

- A new or untouched design still follows the frequency-first workflow.
- A tuned design is never silently resized.
- Off-frequency analysis remains a separate, explicit operation.
- The behavior is testable and consistent across the families with a starting
  helper.

Negative:

- The editor needs a small pristine-state tracker and clear feedback.
- Users who expect every frequency edit to resize a tuned design must use the
  explicit action.
- The existing Yagi behavior remains inconsistent until a follow-up.
- A separate analysis-frequency field is still deferred.

No project schema, solver, or numerical-reference change is required by this
decision.

## Alternatives considered

- **Universal auto-scale on every frequency change.** Rejected: it destroys
  tuned geometry and changes the antenna under test during off-frequency
  analysis.
- **Always require an explicit action.** Rejected as the only path: it adds
  friction to the frequency-first creation workflow.
- **Add a second analysis-frequency field now.** Deferred: the existing sweep,
  band analysis, and measurement-comparison paths already cover the analysis
  use case.
- **Compare every numeric field to detect pristine geometry.** Rejected:
  installation fields and display rounding would create false dirty states.
  Track the fields each starting helper actually overwrites.

## Revisit triggers

Reconsider this policy if:

- users consistently expect a frequency edit to redesign a tuned antenna;
- a dedicated analysis-frequency control is added;
- more families receive deterministic starting helpers;
- the Yagi table is migrated to the same pristine policy or is explicitly kept
  as a documented exception.

## Implementation plan

- **UX35 — implemented 2026-11-17:** pristine tracking, automatic regeneration
  for the five live families, non-modal feedback, and tests. Modal generators
  update locally; project-editor changes remain normal unsaved form edits.
- **UX36 — implemented 2026-11-17:** the quad-beam frequency-first estimator,
  dialog element-count field, registry entry, and apply-preservation path are in
  place.
- **UX37 — implemented 2026-11-17:** explicit scale-to-frequency action for
  non-pristine, allowlisted designs, with a target-frequency dialog and
  approximation warning.
- **HF10 — implemented 2026-11-18:** the Moxon and Yagi forms now use the same
  pristine-state tracker as the other frequency-first families. A pristine
  frequency change regenerates the Moxon scaled reference or scales the Yagi
  table; an edited/loaded design is preserved and shows the stale message.
  Applying the Moxon reference or the Yagi NBS preset resets pristine.
  Newly created templates and applied estimates mark pristine; loaded projects,
  optimizer results, and manual edits mark non-pristine. A gross
  design-frequency mismatch shows a warning, and a grossly mismatched Yagi is
  rejected by the optimizer with
  `optimize.unavailable.frequency_mismatch` before the solver starts.
- The user guide and design-frequency help describe the delivered behavior.
  **Load starting dimensions** remains the explicit path for edited geometry.
